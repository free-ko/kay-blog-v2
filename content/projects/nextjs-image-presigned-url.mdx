# 들어가며

푸시가 나가고 7분 뒤, 서버 CPU가 70%까지 올라갔어요.

서버는 스스로 대수를 늘려서 15분 만에 안정을 찾았어요. 에러도 없었고, 사용자가 느낄 만큼 느려지지도 않았어요. 그냥 넘어가도 되는 일처럼 보였어요.

그런데 이상한 점이 하나 있었어요. **요청은 가벼운데 CPU만 무거웠어요.** 이 글은 그 차이를 따라가다가 `next/image`의 동작 방식을 다시 배우게 된 이야기예요.

**네 줄 요약**

- **문제**: 푸시 직후 CPU가 70%까지 올라 서버가 3대에서 6대로 늘었어요. 그런데 응답 시간과 에러는 평소와 같았어요.
- **원인**: Next.js 서버가 `/_next/image` 요청 14,778건을 받아, 사진마다 리사이즈와 압축을 새로 했어요. 사진 주소가 매번 바뀌어서 결과를 한 번도 재사용하지 못했어요.
- **해결**: 그 사진에는 서버 최적화를 끄고(`unoptimized`), 근본적으로는 업로드할 때 썸네일을 한 번만 만드는 방향으로 정리했어요.
- **배운 점**: next/image 최적화는 같은 사진을 여러 번 다시 쓸 때만 이득이에요.

<br />

## 푸시 7분 뒤 CPU가 70%까지 올라갔어요

저희 서비스는 매달 사용자에게 "월간 리포트"를 보내요. 지난달 내 차를 어떻게 관리했는지 한 화면으로 보여 주는 기능이고, 리포트가 나오는 날에는 앱 푸시로 알려 드려요.

이날 오후 2시에도 푸시가 나갔고, 서버는 이렇게 움직였어요.

```
14:00  ●  푸시 발송
       │
14:07  ●  CPU 70.5% (서버 3대)
       │
14:09  ●  자동 증설 시작 (서버 4대)
       │
14:15  ●  서버 6대까지 증설
       │
14:16  ●  CPU가 기준선 아래로 내려오며 안정
```

### 응답은 평소와 같은데 서버만 바빴어요

| 지표 | 푸시 직후 15분 | 평소 대비 |
| --- | --- | --- |
| 에러 | 0건 | 같음 |
| 응답 시간 | 0.2~0.3초 | 같음 |
| CPU | 최대 70.5% | 크게 높음 |
| Node 이벤트 루프 지연 | 평소의 약 10배 | 크게 높음 |

응답은 평소처럼 빠른데, 서버는 평소보다 훨씬 바빴어요.

> 서버는 **응답 말고 무슨 일**을 하고 있었을까요?

## 첫 번째 가설: 화면 한 번에 같은 API를 세 번씩 불렀어요

원인을 찾는 과정은 크게 세 단계였어요.

```
[가설] API를 3번씩 부른다
   │
   ▼  숫자로 검증
[반증] API로는 CPU의 20%밖에 설명이 안 된다
   │
   ▼  APM 밖을 본다
[발견] CDN 로그에서 /_next/image 요청이 400배
```

가장 먼저 APM(서버 요청 추적 도구)을 열어서, 푸시 뒤 20분 동안 어떤 요청이 많았는지 봤어요.

| 항목 | 푸시 후 20분 |
| --- | --- |
| 월간 리포트 화면 조회 | 3,080번 |
| 콘텐츠 상세 API 호출 | 9,144번 (전체 요청의 43%) |
| 화면 1회당 API 호출 | **정확히 3번** |

코드를 열어 보니 이유가 바로 보였어요. 리포트 아래쪽에 추천 콘텐츠 카드가 3개 있는데, 카드마다 콘텐츠 상세를 따로 불러오고 있었어요. 제목과 썸네일만 쓰는데 본문 HTML까지 통째로 받아오고, 서버에서 그 HTML을 정제하는 작업까지 하고 있었어요.

"아, 이거구나" 싶었어요.

### 그런데 숫자가 맞지 않았어요

원인을 확정하기 전에 숫자로 확인해 봤어요. 분 단위 CPU 사용량과 리포트 조회 수를 나란히 놓으니 둘은 거의 똑같이 움직였어요(결정계수 0.93). 기울기로 계산해 보면 리포트 한 번에 CPU를 약 1초 쓰고 있었어요.

| 리포트 1회당 | 시간 |
| --- | --- |
| 실제로 쓴 CPU (회귀 분석으로 추정) | **약 1초** |
| APM에 찍힌 처리 시간 합계 | 약 0.2초 |
| 의심했던 HTML 정제 함수 (실측) | 0.4ms |

```
리포트 1회당 CPU 약 1초

██████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
└─ 20% ──┘└──────────────── 80% ────────────────┘

█ APM이 보는 부분
░ APM이 보지 못하는 부분
```

API 중복 호출은 고칠 가치가 있는 문제였지만, **CPU 사용량의 80%를 설명하지 못했어요.**

### 서버 하나가 1코어를 넘게 쓰고 있었어요

새로 뜬 서버 하나가 CPU를 1.4코어까지 썼어요.

| 작업 종류 | 실행되는 곳 | 1코어를 넘을 수 있나요? |
| --- | --- | --- |
| 우리가 짠 JavaScript 코드 | 메인 스레드 하나 | 거의 불가능해요 |
| 이미지 처리, 압축, 가비지 컬렉션 | 네이티브 스레드 여러 개 | **넘을 수 있어요** |

Node는 JavaScript를 스레드 하나로 실행해요. 그래서 1코어를 넘었다면 JavaScript 바깥의 작업이 CPU를 쓰고 있다는 뜻이에요.

Next.js가 이미지를 줄일 때 쓰는 `sharp`는 내부에서 C 라이브러리인 libvips를 여러 스레드로 돌려요. 이 단서로 **의심할 대상이 API에서 이미지로** 바뀌었어요.

## 원인 1: APM에 남지 않는 `/_next/image` 요청 14,778건

APM이 보지 못한다면, 서버 앞단에서 모든 요청을 기록하는 CDN 로그를 보면 돼요. 푸시 앞뒤 20분 동안 캐시에 걸리지 않고 서버까지 온 요청을 전부 세어 봤어요.

| 요청 종류 | 푸시 전 20분 | 푸시 후 20분 | 증가 |
| --- | --- | --- | --- |
| **사진 변환 `/_next/image`** | **37건** | **14,778건** | **약 400배** |
| 콘텐츠 상세 API | 7건 | 9,144건 | |
| 월간 리포트 화면 | 2건 | 3,080건 | |

사진 변환 요청 중 99.5%가 월간 리포트 화면에서 나왔고, 분 단위로 겹쳐 보면 CPU 그래프와 거의 같은 모양이었어요.

`/_next/image`는 Next.js 서버 내부에서 처리하는 경로라서, 저희 APM 설정에서는 트레이스가 남지 않았어요. **APM만 봐서는 찾을 수 없었던 이유**가 여기 있었어요.

<br />

## 원인 2: next/image 최적화는 우리 서버에서 일어나요

왜 사진 변환이 이렇게 많았는지 이해하려면, `next/image`가 어떻게 동작하는지부터 짚어야 해요. 매일 쓰던 컴포넌트인데, 이번에 처음으로 제대로 정리하게 됐어요.

`<Image>`를 쓰면 서로 다른 두 가지 일이 **각각 다른 곳에서** 일어나요.

| | 브라우저에서 하는 일 | 우리 서버에서 하는 일 |
| --- | --- | --- |
| **무엇을** | `<img>` 태그와 속성을 만들어요 | 원본 사진을 줄이고 다시 압축해요 |
| **구체적으로** | 지연 로딩, 자리 미리 잡기, `srcset`과 `sizes` 생성 | 원본 다운로드, 리사이즈, WebP 변환, 캐시 저장 |
| **언제** | 렌더링할 때 | `/_next/image` 요청이 들어올 때마다 |
| **서버 부담** | 없어요 | **CPU를 많이 써요** |

### 요청은 캐시 두 겹을 지나요

`<Image>`가 만든 `<img>`의 주소는 원본 사진 주소가 아니에요. 이런 모양이에요.

```
/_next/image?url=<원본 주소>&w=1080&q=75
```

브라우저가 이 주소를 요청하면, 요청은 **캐시 두 겹**을 차례로 지나요.

```
브라우저
 │  GET /_next/image?url=...&w=1080
 ▼
[1] CDN 캐시
 ├─ 있음 → CDN이 바로 반환 (요청이 서버까지 오지 않음)
 │
 └─ 없음
     │
     ▼
    [2] Next.js 서버 이미지 캐시
     ├─ 있음 → 디스크에서 꺼내 반환 (CPU 거의 안 씀)
     │
     └─ 없음
         │
         ├─ ① 원본 사진 다운로드
         ├─ ② 요청 너비로 리사이즈 (CPU 사용)
         ├─ ③ WebP로 다시 압축 (CPU 사용)
         └─ ④ [2]에 저장하고 반환, [1]에도 저장
```

| | [1] CDN 캐시 | [2] Next.js 서버 이미지 캐시 |
| --- | --- | --- |
| 위치 | 서버 앞단의 CDN 엣지 | 각 서버의 디스크 (`.next/cache/images`) |
| 적중하면 | 요청이 서버까지 오지 않아요 | 서버까지 오지만 리사이즈와 압축은 건너뛰어요 |
| 캐시 키 | 요청 주소 전체 (원본 주소 포함) | 원본 주소, 너비(`w`), 품질(`q`), 응답 형식 |
| 공유 범위 | 모든 서버가 함께 써요 | **서버마다 따로** 가져요 |

두 캐시 중 하나라도 적중하면 ①~③의 CPU 비용은 들지 않아요. 그래서 이 기능은 "**한 번 줄이고, 여러 번 다시 쓴다**"는 전제 위에 서 있어요. 처음 한 번만 비용을 내면, 그다음부터는 저장해 둔 결과를 꺼내 주기만 하면 돼요.

반대로 **두 캐시를 모두 놓치면** 요청마다 ①~④를 처음부터 다시 해요. 서버 이미지 캐시는 서버마다 따로 있어서, 자동 증설로 새로 뜬 서버는 빈 캐시에서 시작한다는 점도 기억해 둘 만해요.

Next.js 문서에도 이 내용이 짧게 적혀 있어요.

> Note that images are optimized at runtime, not during the build.

이미지는 빌드할 때가 아니라 요청이 들어올 때 줄인다는 뜻이에요. Vercel에 배포하면 이 작업을 플랫폼이 대신 해 줘서 잘 드러나지 않아요. 하지만 서버를 직접 운영하면 **그 비용이 고스란히 우리 서버 CPU로** 와요.

## 원인 3: 정비 사진은 다시 쓸 수 없는 사진이었어요

리포트에는 "최근 정비" 칸이 있어요. 사용자가 정비를 받을 때 올린 사진을 작게 보여 주는 곳이에요. 코드는 이랬어요.

```tsx
<Image src={imageUrl} alt={`정비 사진 ${index + 1}`} fill className='object-cover' />
```

평범해 보이지만, 이 사진은 "한 번 줄이고 여러 번 다시 쓴다"는 전제를 세 군데에서 깨고 있었어요.

| 전제 | 정비 사진의 실제 상황 | 결과 |
| --- | --- | --- |
| 같은 주소로 다시 요청된다 | 열 때마다 서명이 바뀌는 주소예요 | 캐시 적중 0% |
| 여러 사람이 같은 사진을 본다 | 내 정비 사진은 나만 봐요 | 서명을 빼도 재사용 3.9% |
| 필요한 크기로 줄인다 | 100px 칸에 1,080~1,920px로 만들어요 | 필요보다 10배 이상 큼 |

### 주소가 매번 바뀌어요

정비 사진은 비공개 S3 버킷에 있어요. 그래서 1시간 동안만 열 수 있는 서명을 붙인 S3 주소, 즉 presigned URL로 보여 줘요. 이 서명은 리포트를 열 때마다 새로 만들어져요.

```
# 1st: /photos/abc.jpg?X-Signature=7f3a...&X-Expires=...
# 2nd: /photos/abc.jpg?X-Signature=c91e...&X-Expires=...
                       ^^^^^^^^^^^^^^^^
                       열 때마다 달라지는 서명
```

Next.js 서버 이미지 캐시와 CDN 캐시는 모두 서명이 포함된 원본 주소를 캐시 키에 넣어요. 그래서 서명이 바뀌면 같은 사진이라도 **매번 처음 보는 사진**이에요. 저장해 둔 결과를 한 번도 꺼내 쓸 수 없었어요.

### 사람마다 사진이 달라요

"그럼 서명만 빼고 같은 사진인지 판단하면 되지 않을까요?" 저희도 이렇게 생각하고 계산해 봤어요.

서명을 뺀 사진 경로로만 세어도, 푸시 20분 동안 다시 쓸 수 있었던 요청은 3.9%뿐이었어요. 내 정비 사진은 나만 보니까요.

### `sizes`가 없어서 필요보다 10배 크게 만들었어요

정비 사진이 보이는 칸은 가로 100px 정도예요. 그런데 서버는 이 사진을 1,080~1,920px로 만들고 있었어요. `fill`을 쓰면서 `sizes`를 넣지 않았기 때문이에요.

> If `sizes` is missing, the browser assumes the image will be as wide as the viewport (`100vw`).

이번에 정확히 이해하게 된 부분이라 조금 더 풀어 볼게요. 브라우저는 다음 공식으로 필요한 사진 크기를 정해요.

```
① 필요한 너비 = sizes가 알려 준 표시 너비 × 기기 픽셀 비율(DPR)
② srcset 후보 중에서 이 값보다 크거나 같은 가장 작은 후보를 선택
```

| | `sizes` 없음 | `sizes='100px'` |
| --- | --- | --- |
| 브라우저가 가정하는 표시 너비 | 화면 전체 (폰 기준 390px) | 100px |
| 필요한 너비 (DPR 3 기준) | 390 × 3 = 1,170px | 100 × 3 = 300px |
| 실제로 요청하는 사진 | **1,200w** | **384w** |

`srcset`의 후보 너비는 `next.config`의 `deviceSizes`와 `imageSizes` 설정으로 정해져요. `sizes`가 없으면 계산의 출발점이 화면 전체 너비가 되기 때문에, 작은 칸에도 큰 사진을 요청하게 돼요.

### 서버가 실제로 한 일

푸시 후 20분 동안 Next.js 서버가 실제로 한 일을 순서대로 적으면 이래요.

```
리포트 3,080회 조회
 └─ /_next/image 요청 14,778건
     └─ 요청 1건마다
         ├─ ① S3에서 원본 사진 다운로드
         ├─ ② 100px 칸에 보여 줄 사진을 1,080~1,920px로 리사이즈 (CPU 사용)
         ├─ ③ WebP로 다시 압축 (CPU 사용)
         └─ ④ 캐시에 저장, 하지만 주소가 매번 달라서 재사용 0번
```

> 서버는 **14,778번의 리사이즈와 압축**을 했고, 그 결과를 **한 번도 다시 쓰지 못했어요.**

## CDN 캐시로는 막을 수 없었던 이유

사실 몇 주 전에도 비슷한 일이 있었어요. 콘텐츠 푸시 때 이미지 때문에 CPU가 올랐는데, 그때는 CDN에 이미지 캐시를 붙여서 서버로 가는 요청을 98.6% 줄였어요. [요청 36건 중 34건은 서버가 볼 필요도 없었어요](/docs/origin-traffic-optimization) 글 마지막에 다음 차례로 남겨 두었던 바로 그 작업이에요.

이번에는 같은 방법이 통하지 않아요. 두 사진의 성격이 정반대이기 때문이에요.

| | 지난번: 콘텐츠 사진 | 이번: 정비 사진 |
| --- | --- | --- |
| 사진 주소 | 항상 같아요 | 열 때마다 바뀌어요 |
| 같은 사진을 보는 사람 | 수십 명 | 나 혼자 |
| 캐시로 줄일 수 있는 양 | **98.6%** | **최대 3.9%** |

> 캐시는 **같은 것을 여러 번 볼 때만** 의미가 있어요.

### 검토한 선택지

| 선택지 | 효과 | 문제점 | 결정 |
| --- | --- | --- | --- |
| 이미 붙어 있는 CDN 이미지 캐시에 기대기 | 거의 없음 | 주소가 매번 바뀌어서 적중하지 않아요 | <span style={{ whiteSpace: 'nowrap' }}>❌ 제외</span> |
| CDN에서 서명을 지워 캐시 키 통일 | 최대 3.9% | 서버가 원본을 받을 때 서명이 없어서 비공개 S3 버킷에 접근할 수 없어요 | <span style={{ whiteSpace: 'nowrap' }}>❌ 제외</span> |
| `unoptimized`로 서버 최적화 끄기 | 서버 CPU 부담 제거 | 사용자가 원본 크기의 파일을 받아요 | <span style={{ whiteSpace: 'nowrap' }}>✅ 당장 적용</span> |
| 업로드할 때 썸네일 생성 | 서버와 사용자 모두 부담 감소 | 백엔드 작업이 필요해요 | <span style={{ whiteSpace: 'nowrap' }}>✅ 근본 해결</span> |

답은 단순했어요. 다시 쓸 수 없는 사진이라면, **줄이는 비용을 낼 이유가 없어요.**

<br />

## 해결: 우리 서버가 사진을 줄이지 않게 하기

### 당장은 `unoptimized` 붙이기

```tsx
<Image
  src={imageUrl}
  alt={`정비 사진 ${index + 1}`}
  fill
  sizes='100px'
  className='object-cover'
  unoptimized
/>
```

`unoptimized`를 붙이면 서버에서 사진을 줄이는 기능만 꺼져요. 브라우저 쪽 기능은 그대로 남아요.

| 기능 | `unoptimized` 적용 후 |
| --- | --- |
| 지연 로딩 (`loading="lazy"`) | 유지돼요 |
| 자리 미리 잡기 (CLS 방지) | 유지돼요 |
| `/_next/image`를 거친 리사이즈와 압축 | **꺼져요** |
| 사진을 받는 곳 | 우리 서버가 아니라 S3에서 presigned URL로 바로 받아요 |

`sizes`도 함께 넣어 두면, 나중에 최적화를 다시 켜더라도 필요한 크기만 요청하게 돼요.

### 그럼 사진은 누가 줄이나요?

`unoptimized`를 붙이면 사진 줄이는 일을 사용자 폰이 대신 하는 걸까요? 저도 한 번 헷갈렸어요.

**아니에요. 아무도 줄이지 않아요.** 폰은 원본 파일을 통째로 내려받은 다음, 100px 칸에 맞게 그리기만 해요.

```
[적용 전]
S3 ─▶ 우리 서버 ─▶ 폰
      원본을 받아 리사이즈·압축한 뒤 작은 사진을 전달

[적용 후]
S3 ─────────────▶ 폰
      원본을 그대로 전달
```

| 부담 | 적용 전 | 적용 후 |
| --- | --- | --- |
| 서버의 이미지 처리 CPU | 높음 | **없음** |
| 사용자 데이터와 로딩 시간 | 작은 사진 | **원본 크기** |
| S3가 받는 요청 | 사진 1장당 1번 (서버가 요청) | 사진 1장당 1번 (폰이 요청) |

즉 서버의 CPU 부담이 사용자의 데이터 부담으로 옮겨 가는 거예요. 공짜 해결책이 아니라 트레이드오프라는 점을 알고 선택해야 해요.

### 근본적으로는 업로드할 때 썸네일 한 번만 만들기

원본 사진이 크다면, 사진을 올리는 순간에 작은 썸네일을 한 번만 만들어 두는 게 가장 좋아요. 리포트는 그 썸네일을 바로 받으면 돼요.

| | 지금: 조회할 때마다 줄이기 | 바꾼 뒤: 올릴 때 한 번만 줄이기 |
| --- | --- | --- |
| 줄이는 횟수 | 조회 수만큼 | **업로드 수만큼** |
| 푸시 직후 서버 부담 | 조회가 몰리는 만큼 급증 | 영향 없음 |
| 사용자가 받는 파일 | 작은 사진 (또는 원본) | **작은 썸네일** |

사진은 한 번 올리면 여러 번 보게 돼요. 비용을 내는 시점을 조회에서 업로드로 옮기면 총비용이 크게 줄어요.

<br />

## 성과: 이미지 처리 비용을 서버에서 걷어내기

원인 분석에서 확인한 수치를 기준으로, 수정하면 달라지는 부분을 정리하면 이래요.

| 항목 | 수정 전 | 수정 후 (계산) |
| --- | --- | --- |
| 푸시 20분 `/_next/image` 요청 | 14,778건 | **0에 가까움** (사진을 S3에서 바로 받기 때문) |
| 리포트 1회당 서버 CPU | 약 1초 | **APM이 보는 0.2초 안팎** |
| 정비 사진 1장당 서버가 만드는 크기 | 1,080~1,920px | **만들지 않음** |

수치보다 더 큰 성과는 **판단 기준**이에요. 어떤 이미지에 최적화를 켜고 어떤 이미지에서 끌지, 팀 안에서 같은 기준으로 판단할 수 있게 됐어요.

<br />

## 총 정리

### 1. next/image 최적화는 런타임에, 우리 서버에서 일어나요

이미지 최적화는 빌드 결과물이 아니에요. 요청이 들어올 때 서버가 원본을 받아 줄이고 압축하는 작업이에요. 셀프 호스팅이라면 그 CPU 비용은 우리 서버가 내요. 그리고 그 비용은 **결과를 여러 번 다시 쓸 때만** 이득으로 돌아와요.

### 2. 켤지 끌지는 "같은 사진을 여러 사람이 보는가"로 판단해요

| ✅ 최적화를 켜는 게 좋은 사진 | ❌ 최적화를 끄는 게 좋은 사진 |
| --- | --- |
| 주소가 바뀌지 않는 사진 (배너, 상품 사진, 콘텐츠 썸네일) | 주소가 매번 바뀌는 사진 (presigned URL) |
| 여러 사람이 같이 보는 사진 | 사람마다 다른 사진 (정비 사진, 내가 쓴 리뷰 사진) |
| 원본이 커서 줄였을 때 이득이 큰 사진 | 이미 작게 만들어 둔 사진 (썸네일) |
| | SVG, GIF, 아주 작은 아이콘 |

### 3. `fill`을 쓴다면 `sizes`는 필수예요

`sizes`가 없으면 브라우저는 이미지가 화면 전체 너비라고 가정해요. 100px짜리 칸에도 1,000px이 넘는 사진을 요청하고, 서버는 그 크기로 사진을 만들어요. `sizes` 한 줄이 빠지면 **서버 비용과 사용자 데이터가 함께 몇 배로** 커져요.

### 4. `unoptimized`는 비용을 없애는 게 아니라 옮겨요

서버가 줄이던 비용이 사라지는 대신, 사용자가 원본 크기의 파일을 받아요. 원본이 크다면 결국 업로드할 때 썸네일을 만드는 쪽이 정답이에요.

### 5. APM에 보이지 않는 CPU도 있어요

| 이런 신호가 보이면 | 이렇게 확인해요 |
| --- | --- |
| 요청은 가벼운데 CPU만 높아요 | APM 밖에 있는 CDN이나 로드밸런서 접속 로그를 봐요 |
| Node 프로세스 하나가 1코어를 넘게 써요 | 이미지 처리, 압축, 가비지 컬렉션처럼 JavaScript 바깥의 작업을 의심해요 |

### 6. 그럴듯한 원인을 찾았을 때가 숫자를 한 번 더 맞춰 볼 때예요

API를 세 번씩 부른다는 사실은 충분히 그럴듯했고, 실제로 고칠 가치도 있었어요. 하지만 그 원인으로는 "리포트 한 번에 CPU 1초"라는 숫자를 설명할 수 없었어요. 의심한 코드를 실제로 재 보고 나서야 다른 곳을 볼 수 있었어요.

> 원인 하나를 찾는 것과, 그 원인이 **숫자를 전부 설명하는지** 확인하는 건 다른 일이에요.

<br />

## 마치며

`next/image`는 이름처럼 이미지를 최적화해 줘요. 그런데 그 최적화가 **어디서, 어떤 전제로** 일어나는지 모르면 오히려 서버에 부담이 될 수 있어요.

이번 일은 장애로 번지지 않았어요. 자동 증설이 제 역할을 했고, 사용자도 불편을 겪지 않았어요. 하지만 요청은 가벼운데 CPU만 무거웠던 차이를 따라간 덕분에, 매일 쓰던 컴포넌트가 실제로 어디서 무슨 일을 하는지 처음으로 정확히 알게 됐어요.
